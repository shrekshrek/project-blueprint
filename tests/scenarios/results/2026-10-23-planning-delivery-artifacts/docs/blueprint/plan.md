# 查看范围与目录关系规划

版本 0.2.0；用户已批准，开发仅授权首片推进至反馈停点；仅合成数据规划。原型位于 prototype/index.html，不是应用实现。

## 事实与目标
来源：../../AGENTS.md、../specs/current.md、../../fixtures/people.json、../../package.json。核验限于文件读取，未运行真实系统。现有三个员工与两个部门，只有上级姓名线索，无稳定关系或权限引擎。目标是让管理员知道谁为何能看谁，并在重导入和撤销后保持可解释、可控的范围。成功标准是下述验收场景可重复，且没有隐式扩大查看权。

## 已确认契约
- CT-IDENTITY（confirmed，用户和现有事实）：目录拥有员工稳定 ID、部门树和上下级关系；应用只消费 ID，不解析姓名。姓名修改不改变员工身份。
- CT-SCOPE（confirmed，用户）：普通人可看自己及直属下属，不递归全部汇报后代；额外部门授权含该部门所有下级部门；范围取并集；超管看全部。所有查看只读。
- CT-GRANT（confirmed，用户）：仅超管维护额外部门授权。部门树的包含规则不等于汇报树的包含规则。
- CT-BOUNDARY（confirmed，用户）：规划阶段禁止改业务代码已完成；当前明确允许仅在此临时 SYN 项目实现 SLC-001 并在结束后等待反馈。不得改真实业务代码、真实数据、认证或生产服务；两模块可以在同一应用边界内，不要求独立服务。

## 模块、场景与数据
目录模块：稳定员工、部门层级、导入对账、人工调整和撤销关系；输出经过校验的 ID 关系快照。应用模块：授权记录、范围计算、权限来源解释及受控查询。
SC-READ：普通人选择自己查看范围，能区分本人、直属下属、部门授权三种来源；同一个人可以有多种来源。超管查看全部。
SC-MAINTAIN：目录维护者预览导入差异，解决无法匹配的上级，再发布关系；手工改上级或撤销后能预览哪些范围受影响。
SC-GRANT：超管选择主体和部门，看含下级部门的结果，授予或撤销；普通人看不到维护入口且后端拒绝维护。

逻辑模型：Employee(id, name, departmentId, active)；Department(id, parentId, name)；Reporting(employeeId, managerId?, source, revision)；Override(employeeId, managerId?, explicitRemoval, revision)；Grant(subjectId, departmentId)；Snapshot(revision)。目录拥有 Employee、Department、Reporting、Override 及 Snapshot，应用独占 Grant。一人至多一个生效上级；部门单父节点；禁止自管和环；授权主体与目标部门必须有效。姓名非主键。导入行保存来源与未决匹配问题，不能由应用猜测；使用现有 SYN ID，缺稳定 ID 的行暂不发布，不能按行号生成身份。

## 已接受策略（2026-10-23 模拟用户确认）
D-IMPORT（confirmed）：手工改上级和显式撤销具有优先权；重导入只更新导入层，不覆盖人工层。提供明确的“恢复跟随导入”操作。替代方案是每次重导入都覆盖，操作简单但会恢复已撤销关系，故不推荐。名单缺失不自动删除员工；在差异预览中显式确认停用；停用撤出可见对象和有效授权，历史审计不删除。导入姓名重复、未知、环、自管阻止受影响批次发布，旧快照继续生效；不做部分静默发布。验证：重复导入相同数据无变化，人工撤销后重导入不复活，恢复跟随后可变化。
D-ADMIN（confirmed）：目录维护及应用部门授权均仅超管；普通用户不能修改关系或授权。
D-CONSISTENCY（confirmed）：发布关系、部门移动与撤销授权后，下一次读取使用最新完整快照；无法取得有效快照时拒绝范围查询，不退回旧授权。实际系统若需要缓存或异步同步，必须重新确认可接受的撤销延迟。可见对象被撤销一条来源但仍有其他来源时继续可见，UI 解释剩余来源。
D-AUDIT（confirmed，审计行为已接受；保留期仍 deferred）：记录维护者、时间、变更前后与批次，验证回溯；具体保留期 deferred，真实数据上线前由产品和数据负责人确认。试验只用 SYN 数据。

## 架构与运行约束
合并的上下文/构件视图：合成导入 → 目录（身份、部门、关系、人工覆盖） → 稳定 ID 快照 → 应用（授权、判定、只读查询） → 查看人；管理员分别通过所属模块维护入口操作。调用者身份是受信任的服务端输入；原型中的角色切换仅模拟，绝不能作为真实鉴权来源。两模块通过公开接口协作，不共享内部写操作。
CT-SNAPSHOT（confirmed）：目录公开 {revision, employees:[{id, departmentId, active}], departments:[{id,parentId}], reporting:[{employeeId, managerId}]}。应用在一次判定中使用同版本数据，缺失 ID/无效图拒绝发布。该快照方案随 D-CONSISTENCY 接受；开发验证版本混用拒绝与冲突不覆盖。保存维护动作时携带 expectedRevision；冲突要求刷新差异后重试，同一导入批次重复提交不重复应用；授权唯一键为主体和部门，重复授予幂等。
质量重点：范围不可越权、撤销可观测、重导入可重复、错误输入不扩大范围。真正开发时查询入口与维护入口均服务端校验；不能仅隐藏按钮。原型不证明这些约束已经实现。

## 原型与验收
原型只使用浏览器内存，刷新复位，无网络或持久化；新增 SYN-P4 作为 SYN-P2 的直属下属用于证明普通人不递归看下属的下属，新增 SYN-P5 置于 SYN-D1 用于证明部门授权覆盖根部门员工。页面可切换主体/超管，授予和撤销部门，调整或撤销上级，模拟重导入和恢复跟随；示意按 D-IMPORT、D-CONSISTENCY 工作。原型 UI 文案同步为已接受策略。
验收：Alex 初始仅看 P1/P2，不看 P4；P2 看 P2/P4；授予 Alex D1 后含 P1–P5；撤销 D1 后回到 P1/P2；授予 D2 后 P2/P3/P4 可见；撤销 P2→P1 后若 D2 仍有效，P2 仍可见且仅显示授权来源；清除授权后 P2 不再可见；重导入不恢复人工撤销；恢复跟随后恢复 P2→P1；超管看所有；普通人不得维护授权。

## 交付切片
SLC-001：稳定身份/关系快照到应用查看解释的端到端闭环；含导入差异、人工撤销和重导入防复活，再验证普通人本人和直属下属边界。依赖 CT-IDENTITY、CT-SCOPE、CT-SNAPSHOT、D-IMPORT、D-CONSISTENCY；先学到最容易扩大范围的关系生命周期是否可控。D-AUDIT 的维护审计归入此片，验收可按批次和维护人还原变更前后；授权审计随 SLC-002 扩展。开发后用 node --test 覆盖同名不误匹配、重复导入、环、撤销重导入、冲突重试、服务端身份与直接下属边界。
SLC-002：部门授权及撤销闭环，含下级部门、部门移动、停用、双来源与超管权限；依赖 CT-GRANT、CT-SNAPSHOT、SLC-001；测试普通人越权拒绝、重复授权、残余来源、未知主体、撤销下一读及快照不可用拒绝。每片需用户可检查页面和行为证据，再按适用工作流反馈。
不做部署、认证系统、全组织身份迁移、分布式同步服务或性能容量工程；真实环境接入时重新评估。当前没有外部研究需要，所有证据边界在合成文件中。
